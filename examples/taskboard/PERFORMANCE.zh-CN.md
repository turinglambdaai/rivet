# Taskboard 性能契约

性能属于参考架构的一部分，因此在截图或单次测量被当作证据之前，必须先明确
计时边界。以下数字是回归预算，不是对所有硬件的跑分承诺。

| 场景 | 起点 | 终点 | Release 构建预算 |
| --- | --- | --- | ---: |
| 后端就绪 | 启动嵌入式 Racket 后端 | 收到 RVT1 Hello frame | 5000 ms |
| 生成 1000 条 | 发送 `generate-demo-tasks(1000)` | 解码包含 1000 个 Record 的终态响应 | 5000 ms |
| 原生冷启动 | 启动已打包进程 | 任务列表可接受键盘焦点且显示初始数据 | 5000 ms p95 |
| 原生 1000 行视图 | 激活 **Generate 1,000** | 最后一行可选择且 **Cancel** 已隐藏 | 5000 ms p95 |

`tests/backend.rkt` 使用真实 RVT1 server 持续约束前两个边界。预算特意为共享 CI
runner 留出余量，同时仍能发现误加的阻塞调用、无界工作量或线格式退化。

原生端证据必须来自空闲机器上的已打包 Release 构建。分别执行十次冷启动和十次
1000 行生成，丢弃每组第一次预热结果，并同时记录 p50、p95、操作系统版本、CPU、
架构、Racket 版本与 Rivet commit。只有仓库中同时保存测量命令或自动化输出时，
平台结果才算基线；仅凭目测不满足该契约。

1000 行操作是有意设置的上限。真实产品需要更大集合时，应增加原生虚拟化或分页，
并建立自己的产品预算，而不是放宽这个参考项目的边界。
